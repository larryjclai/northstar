## The core architectural fact

Northstar's UI is a React app inside a Tauri **WKWebView**. Apple's WidgetKit and App
Intents run in **separate processes that only render SwiftUI / execute Swift** — they
**cannot** load the webview or any React code. So a widget is necessarily a small,
hand-written SwiftUI surface, and the only real engineering is **getting data from the
main app to that separate process**. This is identical whether the app is Tauri or React
Native — so it is not a stack decision, and it does not change the "stay on Tauri"
conclusion in [plan 078](078-react-native-mobile-feasibility.md).

## What's actually feasible here (and the good news)

The iOS project is generated by **XcodeGen** from `src-tauri/gen/apple/project.yml`
(confirmed: `name: northstar`, `bundleIdPrefix: app.northstar.finance`, target
`northstar_iOS` with `entitlements: northstar_iOS/northstar_iOS.entitlements`, iOS
deployment target 14.0). That means the Widget Extension target and the App Group
entitlement can be **declared in `project.yml`** (version-controlled, reproducible) rather
than clicked through the Xcode GUI.

**Critical caveat — Tauri owns project generation.** `tauri ios init` (re)generates
`project.yml` and the `.xcodeproj`. A hand-added widget target in `project.yml` may be
**overwritten if `ios init` is re-run**. Before committing to this, we must confirm one of:
(a) Tauri preserves manual `project.yml` additions across builds (it does NOT re-init on
every `tauri ios build`, only on explicit `ios init`), or (b) we keep a patch/script that
re-applies the widget target. This is the #1 risk to de-risk in a spike before full impl.

## App Group — the shared container

Both the main app and the widget extension must join the same **App Group**:

- Identifier: **`group.app.northstar.finance`** (matches the bundle id prefix).
- Added to BOTH targets' entitlements (`northstar_iOS.entitlements` + a new
  `NorthstarWidget.entitlements`).
- **Provisioning reality**: App Groups are an entitlement.
  - **Simulator + free Apple ID**: works for development/testing.
  - **Physical device**: requires the **paid Apple Developer Program ($99/yr)** — free
    provisioning does not grant App Group entitlements on-device. This is the gating cost
    for shipping the widget to your own phone, and the main thing to weigh.

## The data snapshot (privacy-safe by construction)

The main app writes a **tiny JSON file** into the App Group container on each data refresh.
Keep it minimal and non-sensitive — a glance, not a database:

```json
{
  "netWorth": 917962,
  "currency": "TWD",
  "dayChange": 784707,
  "dayChangePct": 588.88,
  "asOf": "2026-06-27T12:00:00+08:00"
}
```

- **NO** holdings, transactions, account names, or tickers — only the headline figure the
  widget shows. This preserves the local-first / privacy invariant even though the widget
  process can read the file.
- Source in the existing code: `buildNetWorthBreakdown(...)` in
  `src/domain/dashboardSummary.ts` already computes `netWorth`; the dashboard already has
  the day-change. The write hooks into the existing data-refresh path (where the dashboard
  recomputes), not a new pipeline.

### The write path — the one genuine design decision

`@tauri-apps/plugin-fs` writes to `BaseDirectory.AppLocalData`, which is **NOT** the App
Group container. The App Group path is obtained via
`FileManager.default.containerURL(forSecurityApplicationGroupIdentifier: "group.app.northstar.finance")`.
Two options to write there:

- **Option A (recommended): a tiny Tauri command in Rust/Swift.** Add a
  `write_widget_snapshot(json: String)` Tauri command; on iOS it calls a Swift
  `@_cdecl` function (same FFI bridge pattern already used for Foundation Models in
  `src-tauri/gen/apple/Sources/northstar/FoundationModels.swift` + `src-tauri/src/lib.rs`)
  that resolves the App Group container URL and writes the file. Reuses an established
  pattern in this repo; no new dependency.
- **Option B: extend `plugin-fs` scope** to the App Group path. Messier — plugin-fs's
  scope model is built around the standard base dirs; the group container isn't one.

Option A mirrors the existing Foundation Models bridge and is the clean fit.

## Widget implementation sketch (for the follow-up plan, not now)

- New target `NorthstarWidget` (app-extension) declared in `project.yml`.
- A `TimelineProvider` that reads the App Group JSON and refreshes (e.g., every few hours
  + on snapshot change). SwiftUI views for `systemSmall` and `systemMedium` families:
  small = "TWD 917,962" + day-change pill; medium = + a tiny sparkline (the widget can
  store a short recent-values array in the same JSON if we want the sparkline).
- ~120–150 lines of SwiftUI. Availability-gate to iOS 14+ (WidgetKit) — deployment target
  is already 14.0.

## App Intents / Siri (phase 2, after the widget)

`AppIntent` structs ("記一筆 / Add expense") that either deep-link into the app's Quick Add
(`northstar://quick-add?...`) or write a pending entry into the **same App Group** file for
the app to ingest on next launch. Because it reuses the App Group plumbing the widget
establishes, it's cheaper to do **second**. Deep-link is simpler and safer than
cross-process writes for a first version.

## Decision points for you

1. **Is on-device worth $99/yr?** If you only want it in the simulator for now, free
   provisioning is fine and costs nothing. Shipping to your phone (or anyone's) needs the
   paid account. Everything else here works either way.
2. **Widget first, then App Intents?** Recommended — the widget establishes the App Group
   + snapshot write that App Intents reuse.
3. **Sparkline in the medium widget?** Adds a small recent-values array to the snapshot.
   Decide if the glance number alone is enough for v1.
4. **De-risk the Tauri-regeneration caveat first?** Recommended: a 30-minute spike to
   confirm a `project.yml` widget target survives `tauri ios build` before writing the
   full SwiftUI. This is the only real unknown.

## Recommended path if you proceed

1. **Spike (½ day)**: add a stub widget target to `project.yml` + the App Group entitlement
   to both targets; run `tauri ios build`/open in Xcode; confirm the target survives and the
   App Group resolves in the simulator. Decide on the paid account.
2. **Plan 086 (Widget)**: the `write_widget_snapshot` Tauri+Swift bridge, the snapshot
   write hook on the dashboard refresh, the `NorthstarWidget` SwiftUI target. Hand-off
   plan; you build/verify in Xcode.
3. **Plan 087 (App Intents)**: deep-link `AppIntent` reusing the App Group.

## Why no executor dispatch / machine gate here

Unlike plans 079–084 (verified via `tsc` / `cargo check` / `npm test`), SwiftUI in a
Tauri iOS target can only be verified by an Xcode build + simulator/device run, which a
headless executor can't do and the advisor can't gate. So this track is **hand-off plans
you execute in Xcode**, with the design pinned down here first. That's the honest model —
flagged so the verification rigor of the earlier plans isn't assumed to carry over.

## Maintenance notes

- Keep the snapshot **minimal** — every field added is a field the widget process can read;
  never put account-level or holdings data there.
- If `tauri ios init` is ever re-run, re-apply the widget target in `project.yml` (keep the
  spike's diff as the reference patch).
- Widget + App Intents share one App Group; one snapshot-shape change touches both.
